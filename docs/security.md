# Security

Threat model, the OWASP Top 10 (2021) audit from 2026-09-27, and the record
of past incidents with the guardrails they produced. Read this before
touching auth, the Telegram link flow, payments, or anything that accepts
user input.

## Threat model (short)

| Asset                         | Where it lives                                                                       |
| ----------------------------- | ------------------------------------------------------------------------------------ |
| Users' financial transactions | `transaction` table, `description`/`amount` AES-256-GCM encrypted (`ENCRYPTION_KEY`) |
| Sessions / credentials        | better-auth (`session`, `account` — bcrypt/scrypt hashes, never plaintext)           |
| Paid plans                    | `user.planStatus`/`planExpiresAt`, activated only by a confirmed PIX charge          |
| Telegram chat ↔ account link  | `user.telegramChatId` — whoever controls the chat reads/writes the account's data    |

Trust boundaries: browser → frontend proxy → API; mobile app → API;
Telegram → bot (in-process calls into backend services, **no HTTP layer, so no
route validation or HTTP rate limiting** — the bot must validate and throttle
on its own); AbacatePay → webhook; external scheduler → `/cron/*`.

## Audit 2026-09-27 (OWASP Top 10 2021)

Severity: **Critical** = account takeover / data exposure without
credentials; **High** = exploitable with low effort; **Medium** = needs
preconditions; **Low** = defense in depth.

| --- | ----- | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------- |
| 1   | A01   | Critical | Bot "link by account ID": anyone who knew an account ID (displayed in the bot menu and on "Minha conta") could link their own Telegram chat to it and read/write/delete that user's finances | Option removed; linking only through the bot's e-mail/password login or the single-use web token                                               | Fixed                      |

### Accepted / deferred

| Item                                                                                                 | Why deferred                                                                                                                          | Revisit                                 |
| ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------- |
| `bun audit`: `mysql2` (high), `deepmerge-ts` (high), `yaml`/`uuid`/`decode-uri-component` (moderate) | Not reachable: `mysql2` is an unused optional driver of better-auth/Prisma (we use SQLite/Postgres); the rest are build/CLI-time only | On every dependency upgrade             |
| No rate limit on non-auth API routes                                                                 | Every route requires a session; better-auth throttles `/auth/*`. Needs a shared store once more than one instance runs                | Before scaling horizontally             |
| `ipAddressHeaders` trusts `x-forwarded-for` as a fallback                                            | Correct behind Railway (`x-real-ip`) and Caddy (overwrites XFF); spoofable only if the API is exposed with no proxy                   | If the deploy topology changes          |
| `SameSite=None` session cookie                                                                       | Required by the cross-site Railway domains; CSRF covered by better-auth's origin check against `trustedOrigins`                       | If frontend/API share a domain          |
| `script-src 'unsafe-inline'` in the CSP                                                              | Inline theme script + TanStack Start hydration; nonces need framework support                                                         | When TanStack Start supports CSP nonces |
| Bot `BOT_PASSWORD_HASH_BASE64` is one password shared by every user of a multi-tenant bot            | Off by default (`TELEGRAM_BOT_USE_PASSWORD_TO_CONFIRM_ACTIONS=false`); product decision pending                                       | Open question in `PLAN.md`              |

### Verification

Regression tests for every behavior change live in
`backend/src/server.integration.test.ts` (chat-ID injection, token race,
DTO, image scheme, CSV cap, validation leak, cron secret),
`payment.service.unit.test.ts` (forged webhook), `secure-compare`,
`encryption`, and the bot's `lockout`/`markdown`/`keyboards` tests.

## Incident log

### 2026-09-19 — ~93 MB compiled binary committed to history

A `bun build --compile` output (`backend/server.exe`) was committed several
times across ~19 pushed commits. Fixed with `git filter-repo` + force push.
**Guardrails:** `.gitignore` blocks `*.exe`; `.husky/pre-commit` hard-blocks
staged `.exe`; the `git-branch-workflow` skill routes all work through a
disposable `dev` branch.

### 2026-09-20 — real secrets committed to `.env.example` and deploy docs

`BETTER_AUTH_SECRET`, `ENCRYPTION_KEY`, a Google OAuth secret, a Resend API
key, a live `TELEGRAM_BOT_TOKEN` and a bcrypt hash were committed instead of
placeholders. Files were cleaned, but the values remain in older commits —
**treat them as compromised and rotate them before making the repo public.**
**Guardrails:** `CONTRIBUTING.md` "Secrets" section and the
`open-source-guidelines-pre-push` skill (diff staged `.env*`/docs for
real-looking values before every push).

### 2026-09-20 — real bank statement (`paa.csv`) tracked

A real Nubank export (third-party names, partial document numbers) was
tracked at `HEAD`; removed from all history the same day.
**Guardrails:** `.gitignore` blocks `*.csv`; `.husky/pre-commit` blocks
staged `.csv` (added 2026-09-27).

### 2026-09-27 — personal credentials in the seed script

Found during the audit above (finding 3). Removed from the working tree; the
old password is still reachable in history and must be rotated wherever it
is used. **Guardrail:** seed credentials come from the environment.

### 2026-09-27 — production API key in an untracked scratch file

`scripts/test.ts` (never committed) hardcodes an `x-api-key` for the
production backend. It was never staged, but the key should be revoked and
the file deleted. **Guardrail:** keep ad-hoc scripts outside the repo, or
read keys from the environment.

### 2026-09-27 — AbacatePay dev credentials in the setup script

`scripts/common.sh` hardcoded an AbacatePay dev API key and webhook secret
(written into `backend/.env` when choosing the "real PIX" setup option).
Found while consolidating the setup scripts. The key is now typed in at
setup time and the webhook secret is generated per install. **The old key
is in git history — revoke it in the AbacatePay dashboard.**
**Guardrail:** no credential of any kind in scripts; the pre-push checklist
covers `setups/` and `scripts/` too.
